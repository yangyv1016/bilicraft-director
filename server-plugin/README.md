# BiliCraft 导播服务（第一阶段）

安装 `bilicraft-director-server-0.1.0.jar` 到 Paper 1.21.11 的 `plugins/`，使用 Java 21。
首次运行检查旧配置 `plugins/BiliCraftAI/config.yml` 的 `world-name`；首次迁移后，以 `worlds.yml` 中的世界 UUID 名单为权威。
升级时移除旧的 `bilicraft-ai-server-*.jar`，避免同时加载两份插件；保留原有 `plugins/BiliCraftAI/`。
插件内部标识仍为 `BiliCraftAI`，命令、权限节点、通道和隐私文件位置保持不变，无须迁移玩家隐私数据。
本轮使用协议 v4，须同时更新客户端与插件，旧版客户端不能继续握手。

通过 LuckPerms 给摄影机账号或摄影机组授予 `bilicraftai.data.read`。该权限默认不授予任何人，OP 也不自动获得。
这是游戏连接中拉取数据、申请观察的调用权限，不是被观察玩家的白名单。普通玩家不需要 Mod 或额外权限。

## 玩家指令

| 指令 | 效果 |
| --- | --- |
| `/aiview stop` | 取消待开始或当前观察，24 小时内不再选中自己；没有当前观察也可以提前设置此冷却 |
| `/aiview blacklist on` | 长期禁止观察自己，直到主动解除 |
| `/aiview blacklist off` | 解除长期黑名单，已有冷却仍然生效 |
| `/aiview status` | 查看自己的黑名单及冷却 |
| `/aiview blacklist add <玩家名或UUID>` | 管理员将指定玩家加入长期观察黑名单，并立即结束其待开始或当前观察 |
| `/aiview blacklist remove <玩家名或UUID>` | 管理员解除指定玩家的长期黑名单，已有冷却仍然生效 |
| `/tell 摄影机账号 停止跟随` | 仅拒绝该账号当前对自己的观察，效果等同 `stop` |

开始前的 15 秒通知仅发给目标玩家，包含摄影机名字和可点击的拒绝、长期黑名单按钮。
按钮携带随机请求 token；仅真实目标可以操作，旧按钮和重复按钮不能影响下一次观察。
玩家停止后由服务端通知对应摄影机退出，无须自行寻找客户端状态。

管理员的 `add/remove` 需要独立权限 `bilicraftai.blacklist.manage`，默认仅 OP；可通过 LP 授予管理组。
摄影机的数据权限 `bilicraftai.data.read` 不包含黑名单管理权。控制台也可执行管理员指令。
按名字操作仅识别在线或服务端已有缓存的玩家，不联网查询陌生名字；未知名字需要改用完整 UUID，或等待玩家上线后重试。
UUID 直接对应持久化身份，可用于离线玩家；不要把离线测试服 UUID 与正式服身份混用。

## 当前行为

- 仅已加入世界允许名单且处于有效区域内的观察者摄影机可以使用协议；每次请求重新检查真实连接账号的权限。
- 摄影机或目标进入 `exclude-regions` 矩形（含边界、全部高度）时撤销数据或观察授权；本阶段不提供边界避让路径规划。黑名单本身不排除周边建筑。
- 候选仅包含 128 格内、10 秒内有活动的可见普通玩家，最多 100 个。隐身、vanish、观察者、冷却及黑名单玩家不返回。
- 15 秒结束时重新校验权限、玩家状态、黑名单和范围；此前客户端只获得 NOTICE，不能开始跟随。
- 同一目标同时最多接受一台摄影机的预告或跟随。
- 跟随总时长为 180～480 秒，客户端可提交计划时长；未指定时由服务器随机选择。移动、累计至少 3 度转头、挥手、交互及建造都更新活动状态。开始跟随后连续 10 秒无动作则结束。
- 预告或跟随期间可申请每次增加或减少 10 秒，只能调整真实发送摄影机自己的当前目标。服务器复查权限、隐私、心跳与活动状态后独立回执；非法时长或增量保留合法观察，失权或目标失效则优先结束。调整不会重置 15 秒预告或无动作计时。
- 跟随期限始终按原开始时间加核准总时长计算。合法缩短至已到期时正常结束；待播计划或尚未核准的客户端显示不能替代服务端许可。
- 玩家传送至少 32 格、跨世界、离线、进入排除区或隐藏时结束。普通结束冷却 30 分钟，主动拒绝冷却 24 小时。
- 客户端心跳超时 10 秒即结束；每条心跳响应一次 HelloReply。协议每秒最多 12 条，候选每秒最多查询一次。
- 黑名单和冷却使用 UUID、epoch 时间，原子写入 `privacy.properties`。开始预告前预留整个观察时长及冷却；实际开始跟随和申请延长时重新覆盖完整期限，延长预留写入成功后才核准，重启不会丢失已预留冷却。
- 配置或隐私文件读取错误会禁用插件；运行中保存失败会禁用全部数据与观察并明确报错。修复后需重启，失败期间未保存的偏好需重新设置。

## 取景点和区域候选

在 `worlds.yml` 对应世界的 `scenes` 列表配置真实地点，默认 `[]`，没有预置虚构建筑或服务器坐标。
旧 `config.yml` 的场景和排除区只在首次迁移时导入默认世界。修改场景后重启插件生效。

每项必须且仅能包含以下字段：

| 字段 | 含义与限制 |
| --- | --- |
| `id` | 稳定且唯一的场景 ID，1～64 UTF-8 字节，不含首尾空白或控制字符 |
| `name` | 菜单显示名称，1～256 UTF-8 字节，不含控制字符 |
| `kind` | `viewpoint` 为水平环绕；`area` 为区域内缓慢 8 字路线 |
| `x`、`y`、`z` | 取景中心的真实坐标，必须是有限数值；始终使用该条目所属的实际世界 |
| `radius` | 水平路径半径，6～48 格 |

每个世界最多配置 64 个场景。客户端机位在中心 `y+4`，因此中心高度必须在该世界 `minHeight`～`maxHeight-5` 之间。
中心在允许区域还不够，中心±半径的整个包围矩形也不能接触排除区或世界边界。
场景 ID 重复、坐标/半径非法、字段错误或范围冲突均会明确报错并停止插件，保留原配置文件。

授权快照同时返回玩家与场景候选。场景的中心距离加路径半径须在摄影机 128 格内，包围矩形涉及的区块必须全部已经加载；
插件仅检查 `isChunkLoaded`，不会为候选主动加载区块。世界边界后来缩小时也会重新过滤不再安全的场景。
候选按距离排序，玩家与场景交替占用包预算，超出协议 30,000 字节的项目不返回，避免截断网络消息。
客户端另行检查本地距离和区块加载，看到候选不代表可以传送过去。

取景点和区域属于非玩家目标，客户端使用本地运镜，无须玩家观察预告；选择玩家仍完整执行原有 15 秒许可和退出规则。

## 世界允许名单

管理员使用下列命令，独立权限为 `bilicraftai.worlds.manage`（默认 OP），控制台也可执行：

| 指令 | 效果 |
| --- | --- |
| `/aiview worlds list` | 列出允许世界的真实名称、UUID、已加载/未加载状态，以及当前已加载但未允许的世界 |
| `/aiview worlds add <实际已加载世界名>` | 精确按实际名称添加当前已加载世界，初始场景与排除区为空 |
| `/aiview worlds remove <世界名>` | 精确按实际或最后已知名称移除允许记录及该世界场景配置，立即撤销其数据/观察授权 |

名称区分大小写，不进行模糊匹配，不按地标名、文件夹印象或下界/末地后缀推测。含空格的实际世界名可直接完整输入。
支持下界、末地和自定义世界；添加不会加载世界，不会传送摄影机。摄影机需要先正常进入该世界，才能请求其候选。
一次快照只返回摄影机当前世界的玩家和场景，观察玩家也必须处于同一世界。

名单以实际 `World#getUID()` 的 UUID 为键持久化，`name` 为最后确认的实际名称；客户端收到的 `world` 是运行时 `World#getKey()` 字符串，
不把 Paper 世界名猜测成客户端 dimension key。已允许世界卸载时撤销当前授权，保留配置；之后重新加载相同 UUID 时重新校验配置并启用。
实际名称变化但 UUID 不变时更新最后已知名称；UUID 改变视为另一个世界，必须重新添加。

生成的 `plugins/BiliCraftAI/worlds.yml` 结构如下，尖括号表示需要使用列表或命令得到的真实值：

```yaml
version: 1
worlds:
  <真实世界UUID>:
    name: <实际世界名>
    scenes: []
    exclude-regions: []
```

每个世界独立配置 `scenes` 与 `exclude-regions`，字段规则与前述相同；不要把这些尖括号占位值复制为真实配置。
未加载世界的配置先校验字段/数值形式；实际加载时才用该世界真实高度和边界校验几何范围，失败会明确停止全部导播数据和观察。
`worlds.yml` 原子保存；读取或写入错误按现有隐私策略处理，不静默回退为全世界允许。

首次不存在 `worlds.yml` 时，插件仅从旧 `world-name` 对应的实际已加载世界导入一次；该世界未加载则记录警告并初始化空名单，
保留原 `config.yml`，由管理员明确添加世界。之后即使名单为空，也不会再次自动导入旧世界。
移除世界会删除它在名单中的场景和排除区；重新添加从空配置开始，操作前可备份 `worlds.yml`。玩家隐私文件和冷却不会删除。

## Dynmap 外链映射

服务端仅保存地图部署地址、明确的 Dynmap 世界标识和现有排除规则，不抓取、解析或缓存地图文件。
摄影机收到轻量元数据后，在本机中控手动拉取时直接连接外链；游戏连接不承载整份地图数据。
普通 Snapshot 仍只返回前述手工场景和玩家，不混入地图文件。

管理员或控制台使用独立权限 `bilicraftai.map.manage`（默认 OP）：

| 指令 | 效果 |
| --- | --- |
| `/aiview map set <实际允许世界名> <Dynmap世界标识> <部署base URL>` | 为已加载且已允许的实际世界建立明确映射，不按世界名猜测 Dynmap 标识 |
| `/aiview map status <世界名>` | 查看已配置地址和 Dynmap 世界，不发起 HTTP 请求 |
| `/aiview map clear <世界名>` | 删除该世界的外链映射 |

实际 Paper 世界名可含空格，填写在最后两个参数之前；Dynmap 标识与部署 URL 使用单个无空格参数。
base URL 是地图部署根地址，例如 `https://map.example/s2/hyperion/`，不是 marker JSON 的完整地址。
只允许 HTTP(S)，禁止账号密码、查询参数或片段；地址不能承载访问密钥。允许明确配置本机 HTTP，用于隔离联调。
客户端请求固定路径 `tiles/_markers_/marker_<编码后的Dynmap世界标识>.json`，禁止 HTTP 重定向。

映射独立原子保存于 `plugins/BiliCraftAI/map-sources.yml`，不修改允许名单或玩家隐私文件：

```yaml
version: 1
worlds:
  <真实世界UUID>:
    name: <最后确认的实际世界名>
    base-url: https://map.example/s2/hyperion/
    dynmap-world: <明确核对的Dynmap世界标识>
```

关联键始终是 Paper 世界 UUID，世界名仅作显示；移除允许世界后该映射不会绕过允许名单，重新允许相同 UUID 时可继续使用。
读取损坏或写盘失败沿用配置故障策略。摄影机每次拉取元数据重新验证真实账号权限和握手。
排除区必须完整下发，单世界超过64条时返回未配置与明确原因，不截断规则。元数据不包含世界边界；客户端执行时仍检查真实边界、已加载区块和排除区域。

客户端导入器最多读取2MiB、等待20秒，拒绝重定向，最多解析4096个点与区域；同源并发请求合并，5分钟内复用缓存，过期使用 ETag 条件验证。
失败保留上次缓存并明确状态；不会定时下载。运行缓存最多保留8个来源，导入场景的磁盘缓存由客户端既有缓存管理。

## 后续范围

服务端没有热力采集、Dynmap 分析、地图 HTTP 代理、区域传送或建筑自动发现。
目前只可观察附近已加载目标。不要将第一阶段 JAR 当作可无人值守整场巡游的正式版本。

测试使用纯 Java 会话域及真实文件系统，覆盖通知截止时间、授权重检、伪造和旧 token、并发目标、时长调整所有权/边界/到期、延长持久预留及读写故障。
真实 Paper 和客户端的联调结果以根项目交付记录为准。
