# 服务端地图与热力数据的拉取方案及负载预算

日期：2026-10-16。地图链路按用户最新要求改为客户端直连外链，Minecraft 服务器只下发外链、世界映射与少量边界规则，不抓取或转发 Dynmap JSON、瓦片。持续热力聚合与分页仍未实现；没有执行线上负载测试。下列成本估算不是实测 CPU、MSPT 或 TPS。

## 默认方案：客户端按需读取外链，不持续采样热力

按用户“负载越小越好、已有 Dynmap 能反映景点和居住地”的选择，首版建议不新增持续热力采样。
管理员为实际世界 UUID 配置外链和 Dynmap 世界标识。客户端手动点击后，先通过游戏连接读取这份小型元数据，再由 Mod 异步直连外链读取 markers/areas 并缓存；原始地图数据不经过 Minecraft 服务器。按钮不扫描世界、不生成热力、不触发 Dynmap 渲染。

建议分别处理三种数据：

- 地图元数据、已有地标：Mod 按需读取既有 Dynmap 标记并缓存到本机。用户提供的地图地址是 `https://map.bilicraft.com/s2/hyperion/`；Minecraft 服务器仅保留链接和显式世界映射。
- 玩家活动/建造热力：默认关闭，仅作为未来明确启用的扩展；本文后面的网格计算属于该可选方案。
- 客户端巡游候选：从缓存热点和管理员场景中选择少量区域，过滤排除区与距离后供客户端本地运镜。

活动热力表示“近期有人活动”，不能直接等同于“建筑密集”。长期无人到访的老建筑仍需 Dynmap 地标、已有场景或其他建筑信息补充。

本轮 Paralon 地图标记核验得到：原始 marker JSON 为 604,572 字节，包含 564 个 point 和 360 个 area，支持 ETag，来源见 [Dynmap 核对记录](dynmap-data-findings.md)。
采用 5 分钟本机缓存有效期，只有缓存过期后的手动点击才发出一次条件请求，单台导播机最频繁约 12 次/小时。
假设每次均变化且完整返回，原始 JSON 约为每台导播机 7.3 MB/小时，未计 HTTP 头和压缩；这部分流量发生在地图站点与导播机之间。ETag 未变化时使用 304，不重新传正文。
缓存有效或同源请求在处理中时复用缓存/任务。未完成或失败时保留旧观景缓存，不阻塞游戏主线程。

默认新增的在线人数相关采样量为 **0 次/秒**，服务端新增 Dynmap 下载/JSON 解析量也为 **0**。HTTP、解析和候选筛选在导播机执行；按响应大小和候选数量限制成本。游戏内仅保存当前世界的少量附近景点，不通过游戏消息搬运原始地图或图片。

## 当前代码已有的成本

客户端本地 WebUI 的 HTTP 服务和每秒状态读取都发生在导播机器，服务端插件不托管网页。状态轮询只读 Mod 当前已有数据；只有人工刷新或切换目标时沿用原游戏协议请求。因此不能把网页轮询频率当作服务端快照/热力采样频率。

当前 [DirectorPlugin](../server-plugin/src/main/java/dev/bilicraft/ai/server/DirectorPlugin.java) 尚无热力图：

- `onMove` 对有效位置变化或明显转头更新活动时间和位置，挥手、交互及建造事件也更新活动状态。活动表按在线玩家保存，是 O(P)，不是完整轨迹。
- `SnapshotRequest` 每个摄影机最多每秒一次；筛选摄影机当前允许世界的玩家、检查排除区、按距离排序，最多取 100 个玩家，不会计算跨世界距离。
- 服务端手工场景仍最多 64 个，快照只检查当前世界；Dynmap 全量候选不进入该服务端列表。半径最多 48 格，包围矩形最多涉及 7×7=49 个区块，64 个手工场景都进入检查时最多 3,136 次 `isChunkLoaded` 查询/快照；不会主动加载区块。Mod 对直连导入的景点先按距离形成最多 128 项短名单，再检查加载与边界，最终合并附近最多 64 项。
- 快照发送按真实 Codec 编码长度交替选择玩家和场景，完整包不超过 30,000 字节。

排除区数量也影响成本。假设 200 在线、100 个排除矩形，一次快照仅玩家的区域检查上限就约为 20,000 次矩形比较；场景另外最多 6,400 次。实际会因提前匹配、距离和其他过滤减少。

当前距离排序在比较器中调用 `getLocation()`，会产生临时位置对象；按每个候选先采集一次位置和距离再排序，可减少分配。这是后续 profiling 的具体检查点，本文没有修改其实现，也不声称当前因此发生 TPS 问题。

## 未来可选热力：每秒与每 tick 采样的工作量

只有未来主动开启热力扩展时才产生下表工作量。假设服务器 20 TPS，每个在线玩家每次采样更新一个网格单元；不含建造事件。移动事件实际触发频率随玩家活动和网络包而变，不能把移动事件数机械当成固定每秒 20 次。

| 在线人数 | 每秒一次 | 每 tick 一次 | 每小时样本，每秒一次 | 每小时样本，每 tick 一次 |
| --- | ---: | ---: | ---: | ---: |
| 50 | 50 次/秒 | 1,000 次/秒 | 180,000 | 3,600,000 |
| 100 | 100 次/秒 | 2,000 次/秒 | 360,000 | 7,200,000 |
| 200 | 200 次/秒 | 4,000 次/秒 | 720,000 | 14,400,000 |

每秒采样只有每 tick 的 1/20 工作量，足够给缓慢巡游选择热点。现有跟随、静止判断仍保留事件粒度，不随热力采样一起降频。

建议主线程只读取玩家状态、计算网格坐标并提交普通数据；热力索引、衰减、排序和文件序列化使用独立数据处理任务。异步任务不能读取 Bukkit 玩家、世界或方块对象。新热力功能也不应在现有 `onMove` 中追加全量排序、文件写入或世界扫描。

热度使用时间戳按需衰减。不要每秒遍历历史上所有单元只为统一乘一次衰减系数；访问单元数 H 可能远大于在线玩家数 P。

## 未来可选热力：网格大小与内存

仅举例一个 10,000×10,000 格范围，不代表 Hyperion 实际面积。计算为 `ceil(边长/网格边长)²`，且这里按整个范围全部产生记录估算：

| 网格 | 全覆盖单元 | HashMap 对象实现估计 | 紧凑 16 字节/单元估计 |
| --- | ---: | ---: | ---: |
| 16×16 | 390,625 | 35.8～59.6 MiB | 5.96 MiB |
| 64×64 | 24,649 | 2.26～3.76 MiB | 0.38 MiB |

HashMap 估计假设单元合计约 96～160 字节，包含键、节点、热度/时间对象及桶表摊销，具体取决于 JVM 布局和实现。紧凑数组假设两个 4 字节热度加一个 8 字节时间戳，不包含索引、缓存副本、文件缓冲与 JVM 自身内存。

若以后启用热力，建议选择 64×64 稀疏网格，仅保存产生过活动的单元，设置到期清理与硬上限。例如 100,000 个活跃单元对应上述 HashMap 假设约 9.2～15.3 MiB；生成缓存或持久化快照时还需预留副本空间。确有局部精细需求再对热点区域使用 16×16。默认方案不会分配这些热力网格。

64×64 对同面积约减少至 16×16 的 1/16 单元数；在线采样次数并不减少，减少的是历史单元、排序和下发规模。

## 未来可选热力：写盘与缓存刷新

推荐只持久化聚合单元，不逐次写入玩家轨迹。每 5 分钟异步批量写入脏单元或完整紧凑快照，关闭时完成受控落盘；活动热力不与必须及时保存的玩家拒绝/黑名单共用高频文件写入流程。

若聚合快照每单元使用 32 字节，100,000 单元为约 3.2 MB，每 5 分钟一次约合 10.7 kB/秒；若 JSON 为每单元约 80～160 字节，则单份约 8～16 MB，平均约 26.7～53.3 kB/秒。以上未包含压缩与文件系统开销。平均带宽很小，也不能证明把整份序列化和写盘放在主线程不会卡顿。

反例：如果每个原始采样都写 64 字节，200 人每秒采样一天约 1.11 GB，每 tick 采样一天约 22.1 GB；这类累计日志不是推荐存储方式。

热点列表缓存建议每 5～15 秒生成一次，开始可用 10 秒。取前 K 个热点可用有界 Top-K，避免每次按钮都对全部 H 个历史单元排序。缓存携带版本、生成时间和覆盖范围，更新未完成时继续返回上一份，而不是阻塞客户端请求。

## 手动拉取与 30KB 包限制

当前协议 v2 的 `Snapshot` 只承载玩家和 `SceneView` 列表，已经能由菜单手动刷新；它没有地图瓦片或原始热力网格消息。可以把未来分析出的少量热点转换成场景候选，但完整热力网格需要显式扩展协议，不能把图片/任意 JSON 塞进场景字段。

建议按钮默认拉取当前范围或前 200～1,000 个热点，而不是整张地图。若未来二进制单元暂按 `gridX/gridZ` 两个 32 位整数、两项 16 位热度，共 12 字节估算：

- 200～1,000 单元约 2.4～12 kB，加元数据后通常可以放入一包。
- 分页每包使用约 24 kB 数据预算、约 2,000 单元，其余留给版本、世界、范围、缓存版本和页号等字段；总包仍不得超过 30,000 字节。
- 示例 64×64 全图约 296 kB、13 页；16×16 全图约 4.69 MB、196 页，均不含分页头和压缩。
- 若每个摄影机最多 2 页/秒，满页带宽约 48 kB/秒；上述完整拉取分别约需 6.5 秒和 98 秒。这解释了为何应优先局部范围和热点摘要。

每次请求重新校验真实发送账号权限。按钮可冷却 1～2 秒；缓存按内容版本复用，同一版本不重算，多个摄影机也共享已生成的数据。大地图瓦片宜继续由已有地图站点按需提供，游戏消息通道承担小型结构化数据。

多世界缓存需要按实际世界分开，导播世界允许名单已经按 UUID 管理；Dynmap 标识与运行时 dimension key 的对应仍需明确配置，不能按同名猜测。
WebUI 和 AI 通过 Mod 的统一入口读取状态或选择队尾候选，不分别抓取另一套地图或热力数据。客户端直连外链标记导入与 AI 短决策已实现；热力聚合及远程中控仍未实现，本地运镜和缓存降级继续保留。

## 最重要的瓶颈与验收目标

默认地图方案先关注 HTTP 延迟、ETag 命中率、响应/缓存大小、异步解析耗时、是否错误地在主线程等待网络，以及重复点击是否只使用一份缓存。50/100/200 人不会按人数倍增同一地图文档的下载次数。

优先避免的是强制加载/生成区块、遍历世界方块、Dynmap 重渲染、主线程全图排序/序列化/写盘，而不是每秒 200 次简单网格累加。建造统计依靠事件；WorldEdit 等批量编辑是否触发标准方块事件需要单独核对，不能假定热力已经覆盖所有编辑方式。

后续实现的预算目标可以设为：单个主线程热力工作批次尽量不超过 1 ms，超预算时把采样分摊到多个 tick；后台缓存构建不堆积，旧缓存可读；内存单元数、队列长度、脏单元与输出带宽均有上限。这些是需要实测检验的设计目标，不能据此承诺固定 CPU 百分比或零 TPS 影响。

建议在相同地图、人数和活动强度下比较关闭/开启功能，至少记录：

- 50/100/200 人采样下的 MSPT 分位数与超过 50 ms 的 tick 数；分别统计采样、缓存换代和落盘期间。
- `onMove`/活动更新、候选扫描排序、场景区块检查、Codec 的调用数及分配量。
- 1/5 个摄影机同时手动刷新时的延迟、GC、主线程开销和每秒输出字节。
- 历史单元增长后的堆占用、Top-K/衰减耗时、缓存年龄、写盘耗时与队列峰值。
- 保证热力管线不增加区块加载/生成数，不把正式服 Dynmap 已有渲染负载算作简单采样成本。

Paper 1.21 起内置 spark，可用于上述方法级 CPU 和 GC 分析，实际应在问题或相应负载发生时采样；官方给出的示例命令是 `/spark profiler start --timeout 600`。[Paper profiling 文档](https://docs.papermc.io/paper/profiling/)

本文没有执行这些负载场景。当前构建、单元和本机协议/客户端验证不能替代 50～200 在线及正式服务器硬件上的负载测试。
